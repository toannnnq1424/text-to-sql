# Dataset-aware analytics and actionable semantics

Baseline for `module/analytics-experience`, correcting the user review of 2026-10-21. Keep React→Java→private Python; engine enums, existing Candidate and result precision remain unchanged.

## Suggestions and semantic ownership

GET `/datasets/{id}/question-suggestions` returns the normal Page of `{suggestionId,question,description,category,origin,chartType,tableRefs,selectedMetrics,selectedDimensions,sqlDialect}`. Origin enum: `PHYSICAL_SCHEMA`, `SEMANTIC_MODEL`, `CURATED`. Categories and content are computed from the authorized current physical schema and active semantic model, never from an unrelated sample dataset. No result values are fabricated. Schema suggestions may propose counts, grouped distributions and time/measurement analysis only where actual columns/metadata support them. These proposals use physical column names and do not assert their business meaning. The model may answer a clearly named physical-column operation without configured semantic definitions; before returning a candidate it must preserve explicitly requested SUM/AVG measures rather than substituting another aggregate. Semantic suggestions use declared metrics and compatible dimensions. Curated examples remain explicit administrator configuration; label them as approved examples, not AI-generated live answers. A new dataset works with empty semantics and has its own schema-derived suggestions. Warehouse/dataset change clears stale forms/results/suggestions. Search/category/page parameters use existing conventions. Schema/model provenance appears in UI.

POST `/datasets/{id}/semantic-assist`, ADMIN only, accepts `{instruction:string}`1..2000 and returns `{model,semanticModel:Context,warnings:string[]}`. It calls the configured model, not deterministic fixtures, to propose metrics/dimensions/rules/descriptions over the authorized current metadata. Python receives no data rows/credentials. Model proposal is strict/size-bounded and validated against actual columns, compatible dimensions and the source-fork business compiler; Java independently validates the merged proposal before response. It never activates or writes warehouse data. Existing definitions are preserved unless a proposed item explicitly has that name. Admin reviews/edits a new semanticVersion and activates through existing validate/PUT. Unsupported/invalid proposals and provider outages are controlled errors; no silent fabricated fallback. Physical descriptions come from discovery; business descriptions are stored admin configuration/proposals, editable and labeled accordingly.

Private POST `/internal/v1/semantic-assist` takes `{correlationId,warehouseId,datasetId,sqlDialect,semanticContext,instruction}` and returns `{model,metrics:Metric[],dimensions:Dimension[],businessRules:string[],warnings:string[]}`. Same auth/correlation/body/privacy limits as generation. Core business definitions are not embedded in React or bootstrap for arbitrary datasets.

## Query SQL and presentation

Candidate eight-field generation contract stays unchanged. Public Query detail adds nullable `candidateSql` (default null for older snapshots) for the original model/compiler output. On SUCCESS, `generatedSql` is the final logical SQL normalized by Java SqlGuard and passed to the executor. A failed Query can retain planned SQL from before guard acceptance; UI must show its failure status and must not label it successfully executed. The adapter may add its fixed SELECT/LIMIT transport envelope for PostgreSQL/MySQL or cursor bounds for SQL Server; this infrastructure envelope does not replace the displayed logical query. History summaries may omit candidateSql. Native planning still runs; source-fork AST simplification removes redundant generated CTE/projection wrappers only when semantics can be preserved, retaining meaningful user CTEs/aggregates/joins/filters/limit/null/precision. Post-rewrite source-set and Java validation remain mandatory. Never show short candidate SQL as if it were executed when it differs.

Final chart choice is validated from real result types/shape: a numeric scalar prefers number; categorical+numeric data supports bar/pie, time+numeric supports line/area, compatible multiple measures support grouped bar. Unknown/unsafe specs remain a table with a reason. Unit compatibility and finite-number display bounds are enforced. Field labels/units use matching active metric/dimension metadata when available, otherwise actual result column metadata; no domain-specific field guesses. UI supports chart axis/series selection for compatible result columns, a useful scalar card, bounded chart canvas, compact one/two-column tables, stable spacing and no nested blank full-width shells. Copy/export preserve exact decimal/bigint strings.

## Catalog actions and evaluation

Catalog metrics expose create/edit/explore actions routed to the active semantic editor/query builder with an explicitly selected metric; mutations retain ADMIN validation/version/audit. Model assistance is a reviewed draft, not inferred business truth. Query readers remain read-only; adding application-level semantic/source/import/pipeline actions does not grant arbitrary LLM/SQL write access.

Evaluation reference SQL is an explicit regression oracle, not generated live truth or a model answer. Existing packaged suites are shown as dataset-specific and can run only when all references validate against the selected dataset. UI must not keep an unrelated default suite when switching warehouses. Dataset-derived checks may be generated from actual schema/approved examples, with provenance and independent result comparison; do not report a template corpus as general AI accuracy.

GET `/evaluation/test-suites?datasetId=...` returns only compatible packaged suites plus `dataset-schema`, with additive `origin:CURRENT_SCHEMA|PACKAGED_REGRESSION` and `description`. The schema suite independently executes COUNT oracles over up to8 authorized actual tables; mode API/AUTO is required (DETERMINISTIC400). Runs record `suiteId` and `referenceOrigin`. Calls without datasetId retain packaged-suite listing for existing automation. Basic schema checks do not measure broad model accuracy.

POST `/evaluation/run` persists and returns `RUNNING` immediately with HTTP202. A bounded pool (2 workers,8 queued runs) keeps the authenticated principal/correlation, frozen input and progress; the client polls existing run/results endpoints. Full queue returns429 `EVALUATION_BUSY`. Per-case authorization/configuration is rechecked; configuration changes fail the run instead of mixing versions. A20-minute task bound complements each query deadline. Restart marks interrupted RUNNING runs FAILED with `EVALUATION_INTERRUPTED`, retaining completed cases and making no automatic model replay. Run adds optional nullable `error` for controlled failure; case `failureReason` explains chart mismatch separately from SQL-result equivalence.

## Complete chart snapshots

Query detail contains a bounded preview, normally20 rows. Overview/Visualization read the existing result-page API (100 rows/page) when needed, never regenerate SQL or call a model to fill the chart. Plot up to1000stored rows/5MiB; preserve returnedRowCount/truncation and explicitly state when additional snapshot rows exceed the chart bound. Inconsistent/expired/failed pages produce an error, not a silent preview fallback. Table/CSV retain their existing snapshot paging and permission/expiry policy. No public DTO or endpoint changes.
